# Issue Intent Audit

在实施前输出以下审计结构，避免被 issue 中过时或次优建议误导。

## 1) 需求目标

- 当前 issue 要解决的真实问题是什么？
- 完成后业务或用户体验会如何变化？
- 成功的最小验收信号是什么？

## 2) 现状事实

- 从代码中确认的当前行为（文件/模块级事实）。
- 从 issue/评论中确认的上下文事实。
- 与当前 issue 相关的最近 PR 事实（已合并/进行中）。

## 3) 过时引导识别

- issue 中哪些实现建议可能过时？
- 为什么可能过时（代码已变化、架构迁移、已有替代方案）？
- 若直接照做，可能造成什么风险？

## 4) 候选策略

- 策略 A（推荐）：适用条件、优点、风险、回滚方式。
- 策略 B（次选）：适用条件、优点、风险、回滚方式。

若存在高影响分歧，先与用户确认再实施。

## 5) 待确认决策

- 仅列出高影响、无法从上下文推断的问题。
- 每个问题给出 2-4 个可执行选项和推荐项。

## 6) 审计结论

- 本轮是否可以进入实现阶段？
- 当前假设与边界是什么？
- 需要延后到后续 issue/PR 处理的项有哪些？
